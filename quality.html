Case study 06 · Trust in the numbers

If a number can't be explained, it doesn't ship

Engines that decide stock and money every day need more than correct code on the day they are written. This is the safety net built around all of them: tests that replay real days, audits that read every output, and comparisons with the physical world.

Applies toAll engines and reports
RunsOn every change · every day
Ground truthReal sales · physical counts
ToolsPython · git · SQL
Five layers

From "it runs" to "it's right"

  1. Input gatesStop when data is stale, partial or from the wrong month, before anything is computed.
  2. Regression replayReal SQL answers recorded once per weekday and replayed offline after every code change.
  3. Rule auditA dozen business rules checked on each day's output before it is sent.
  4. Reality checksRebuilt stock against system stock and physical counts; forecasts against what actually sold.
  1. BacktestsNew models judged day by day with only the information available that morning.
  2. Cell-by-cell diffsEvery report and dashboard regenerated before and after a change and compared cell by cell.
  3. Decision logEach rule change written down with the date, the reason and its measured effect.
  4. gitOne commit per validated change, so any past result can be reproduced.
Regression replay

A photograph of each weekday

Some rules only fire on certain days: Thursday covers the weekend, Friday covers Monday, some days allow no supplier surplus. So the harness keeps one snapshot per weekday: the SQL answers, the editable config and the frozen date.

record: each query → hash(sql + params) → stored answer
replay: same query → same answer → compare output row by row

The result is either OK or a list of what changed, with examples (store / product: before → now). An intended change is accepted explicitly, never silently.

Rule audit

Read the output like a reviewer would

  • Whole, non-negative units only.
  • Goods only to store × product pairs that are in the range.
  • Never more than the supplier has.
  • No surplus on the days it is not allowed.
  • Stores not open yet receive nothing they already have.
  • Stock + order never above what can be sold before expiry.
  • New-store caps and new-product rules applied as written.

Bugs the net caught

Each one would have shipped quietly

A random average

The replay showed a mean changing at the second decimal between identical runs: a set iterated in random order. Every list behind an average is now sorted.

A double-counted day

Comparing rebuilt stock with system stock exposed one day of sales subtracted twice in the inherited formula. The fix and the decision to keep or drop it were written down with their measured effect.

Inflated safety buffers

Buffers for multi-day covers summed standard deviations instead of variances, inflating them by up to 70%. Caught by reading the audit columns, fixed with a before/after test.

Surplus to the wrong stores

When most lines of a product were new, surplus went only to the two stable stores, which received hundreds of units each. The audit flagged it the same morning and the file was regenerated.

An export from the future

An HR export arrived with every store's window in the next month. A guard now takes the month from the data itself and corrections live in a separate sheet that survives re-exports.

Outcome. Changes ship weekly without fear: every engine has a replayable test, every daily file is audited before it leaves, and every model is judged on real outcomes. When someone asks "why this number?", the answer is a row, a rule and a date.
